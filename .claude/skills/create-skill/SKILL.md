# スキルの作り方

## 1. まずスキルにすべきか判断する

スキルは「特定の作業をするときだけ読み込まれる手順書」です。作る前に他の仕組みと比べる。

| やりたいこと | 使うもの |
|---|---|
| 特定の作業のときだけ手順を思い出させたい | **スキル** |
| 常に守らせたいルール（命名規約・レイヤー構造など） | `CLAUDE.md` / `.claude/*.md` |
| 「〜したら必ず〜する」を機械的に実行させたい | hook（`settings.json`） |
| 独立したコンテキストで調査・レビューさせたい | サブエージェント（`.claude/agents/`） |
| 人間が明示的に打つ定型プロンプト | スラッシュコマンド（`.claude/commands/`） |

判断基準は**常時必要かどうか**。常に効いてほしいならスキルにしてはいけません。スキルの本文は呼ばれるまで読まれないからです。

「毎回〜して」と言われた場合、スキルでは応えられません。hookかCLAUDE.mdに誘導すること。

## 2. 置き場所とファイル構成

```
.claude/skills/<skill-name>/
├── SKILL.md              # 必須。これだけでも成立する
├── references/           # 任意。詳細な資料
│   └── template.md
├── scripts/              # 任意。実行するスクリプト
└── assets/               # 任意。テンプレートファイルなど
```

- **プロジェクト用**: `.claude/skills/`（リポジトリにコミットされ、チーム全員が使う）
- **個人用**: `~/.claude/skills/`（全プロジェクトで使えるが、Git管理外）

リポジトリ固有の作業ならプロジェクト用、汎用的な道具なら個人用に置く。

ディレクトリ名は `name` と一致させること。

## 3. frontmatter

```yaml
---
name: create-skill
description: <何をするか>。<いつ発動するか（トリガー語を含める）>。
---
```

| フィールド | 必須 | 内容 |
|---|---|---|
| `name` | ○ | 半角小文字・数字・ハイフンのみ。ディレクトリ名と一致させる |
| `description` | ○ | 後述。**ここが最重要** |
| `allowed-tools` | | 使用可能なツールを絞りたいときだけ書く（例: 読み取り専用にする） |

## 4. description の設計（最重要）

**セッション開始時に読み込まれるのは `name` と `description` だけ**で、本文はスキルが呼ばれてから読まれます。つまり**発動するかどうかは description だけで決まります。**

本文がどれだけ良くても、description が弱ければ一度も呼ばれません。

### 書き方

**「何をするか」と「いつ使うか」を両方書く。**

```yaml
# 悪い: 何をするかしか書いていない → 発動しない
description: マイグレーションファイルを作成する。

# 良い: トリガーが具体的
description: マイグレーションファイルを新規作成するときに使う。mst/trx/sys/logのどのグループに置くか、
  シャーディング対応の $connections 配列が必要かを判断して雛形を作る。「マイグレーションを作って」
  「テーブルを追加」「カラムを足して」などで発動する。
```

### 守ること

- **ユーザーが実際に使う言葉をトリガー語として入れる。** このプロジェクトは日本語でやり取りするので日本語を主にしつつ、`SKILL.md` `phpstan` のような英語の固有名詞も併記する
- **具体的な名詞を書く。** 「データ処理」ではなく「マイグレーション」「シャーディング」「ログインボーナス」
- **否定形で範囲も切る。** 誤爆しやすいスキルには「〜のときは使わない」を1文足す
- 三人称で書く（「〜するときに使う」）。一人称や呼びかけにしない

### 発動しないときの直し方

本文ではなく description を疑うこと。ユーザーが実際に打った言葉を description に足すのが最短です。

## 5. 本文の書き方

**読者はClaudeであってユーザーではありません。** 解説文ではなく作業指示を書く。

```markdown
# 悪い: 一般論の解説
マイグレーションはデータベーススキーマを管理する仕組みです。Laravelでは...

# 良い: このリポジトリでの手順と判断
1. 対象グループを決める。マスタ→`database/migrations/mst/`、トランザクション→`trx/`
2. trx配下は `$connections = ['trx1', 'trx2']` を必ず書く。片方だけに流すと不整合になる
3. `--path` は相対パスで渡す。絶対パスは黙って無視される
```

### 守ること

- **命令形で書く。** 「〜すること」「〜を確認する」
- **判断基準を書く。** 分岐があるなら条件を明示する
- **理由を1行添える。** 理由がないと状況が変わったときに応用できない
- **一般的なベストプラクティスは書かない。** Claudeが既に知っていることを繰り返すと、本当に必要な情報が埋もれる。**このリポジトリ固有の事情だけを書く**
- **本文は短く保つ。** 目安200行以内。超えるなら `references/` に分割する

## 6. 段階的開示

SKILL.md には「判断と手順」だけを置き、長い資料は別ファイルにして本文から参照する。

```markdown
詳細な雛形は [references/template.md](./references/template.md) を参照。
```

こうすると、スキルが呼ばれても必要なファイルだけが読まれます。SKILL.md に全部書くと、使わない情報まで毎回コンテキストを食います。

## 7. 動作確認

作ったら必ず確認すること。

1. **`/` を打って一覧に出るか。** 出なければ frontmatter の書式か置き場所が誤っている
2. **`/<skill-name>` で明示的に呼べるか。** 本文が意図通り読まれるか確認する
3. **自然な言い回しで発動するか。** ユーザーが実際に使いそうな表現で試す。ここで発動しなければ description を直す
4. **実際に作業をやらせてみる。** 手順に穴があれば埋める

3が一番飛ばされやすく、一番効きます。

## 8. よくある失敗

| 症状 | 原因 | 対処 |
|---|---|---|
| 一度も発動しない | description にトリガー語がない | ユーザーの実際の言い回しを description に足す |
| 関係ない場面で発動する | description が広すぎる | 対象を具体化し、「〜のときは使わない」を足す |
| 発動するが役に立たない | 一般論しか書いていない | リポジトリ固有の判断・落とし穴に書き換える |
| 「毎回やって」に応えられない | そもそもスキル向きでない | hook か CLAUDE.md に移す |
| 本文が長すぎて読まれきらない | 全部SKILL.mdに書いた | `references/` に分割する |

## 9. 雛形

新規作成時は [references/template.md](./references/template.md) をコピーして埋める。
