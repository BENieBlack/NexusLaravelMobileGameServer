# 同じプレイヤーの同時リクエスト（409 / 503）と再試行

同じプレイヤーの書き込みリクエスト（GET 以外の、認証済みの API）は、サーバーが1つずつ処理する（`api/app/Http/Middleware/LockPlayerRequest.php`）。
trx は「読む → メモリで計算 → 絶対値でUPDATE」で書くため、同時に走ると後から書いたほうが先の更新を上書きする。これを防ぐ。

| ステータス | 意味 | クライアントの対応（推奨） |
|---|---|---|
| 409（`error_code` 40900） | 同じプレイヤーの別リクエストが処理中で、最大5秒待っても順番が来なかった。または、同じ `X-Unique-Request-Identifier` のリクエストが処理中 | 0.5〜1秒あけて、同じ `X-Unique-Request-Identifier` で再送する（最大3回）。冪等性があるので、先のリクエストが成功していれば、同じ結果が返る |
| 503（`error_code` 50300） | ロックの置き場（Redis）に繋がらない。同時更新で上書きされるのを避けるため、処理しない | 少し待って再送する |

- 書き込み API は、画面の連打を防ぎ、前のリクエストが終わってから次を送るのが望ましい
- ロックの保持は最大30秒（リクエストが落ちても自動で外れる）。待ち時間は `security.player_lock.wait_seconds`（既定5秒）
- サーバーは、ロック待ちが500ms以上かかったとき（info）、409 を返したとき（warning）、503 を返したとき（error）に、ログ（`Player request lock ...`）を残す。件数が増えたら、待ち時間や重い処理を見直す
- 負荷試験では、同じプレイヤーへの同時リクエストでの 409 の割合と、ロック待ちの分布を見て、待ち時間（5秒）と保持時間（30秒）が妥当か確認する
